> 流程遵循用户指定：**测试先设用例 → 开发改 → 我验证 → 不过退回开发继续改，直到全清**。
> 纪律：只读他人会话；写只用自建会话并列出 id；**不向 `session-00723a9e` 发消息**；**不重启 DSH**。

## 0. 分叉结论：**网关侧能力完备，bug2/bug3 根因 100% 在 App 侧**

我独立实测（两个探针，均只写自建会话）：

| 探针 | 结果 |
|---|---|
| `probe-fork-push.mjs` | 建会话 `session-3ac26504…` → 订阅 → 发 prompt：**40 条 `session.event`，首次事件延迟 0ms**，36/40 带 `streamKind`；REST `/messages` 同步落库 4 条 |
| `probe-sync-capability.mjs` | 建会话 `session-1bacac3d…` → 订阅 → **第 1 轮发 prompt 得 275 条事件 → 回合结束（status 变 idle）→ 不重订阅，第 2 轮再发 prompt 又得 349 条事件**；另收到 **3 条 `session.status`**（running/idle） |

**判定（决定性证据）**

1. 网关 WS **确实实时推** `session.event`（seq 递增、内容完整）
2. **`session.status` 也在推**（running ↔ idle）
3. **同一订阅在多轮之间持续有效**（第 2 轮不重订阅仍收到 349 条）⇒ 网关**不存在"只推一次"缺陷**
4. 事件携带正确 `sessionId` ⇒ 网关**无串台**
5. REST `/messages` 与 `/sessions` 列表项（`messageCount`/`lastMessagePreview`/`status`）同步更新

⇒ **开发应只改 App 侧**（订阅生命周期 / 事件应用 / UI 重组 / 加载策略）。若开发改网关，属误判方向。

> 附带修正 PM 提到的统计坑：我的探针一律用 `f.type === 'session.event'` **精确匹配**，未踩短键统计的坑。

## 1. A 组 —— bug1 启动加载策略（客观判据，不用"感觉卡"）

| ID | 判据（客观、可机器判定） | 方法 |
|---|---|---|
| **A1** | 冷启动→"左栏工作区列表出现"期间，App 发出的 `/rc/v1/*` 请求**总次数与路径清单** | 真机 `adb logcat` + OkHttp 事件监听埋点；或网关侧加**只读请求计数**（推荐，见 §5 建议） |
| **A2** | 启动阶段**未**请求未展开工作区的会话列表 | 同上，检查是否出现 N 次 `/sessions?workspace=<未展开>` |
| **A3** | 启动阶段**未**请求任何会话的 `/messages` | 同上，`/messages` 出现次数应为 **0** |
| **A4** | 点击展开某工作区后，**此时才**出现该工作区的 `/sessions` 请求 | 冷启动 → 点击 → 比对请求序列 |

## 2. B 组 —— bug2 PC 更新不同步（最严重）

**构造**：在我自建会话上用网关 API 发 `mode:'queue'` 的 prompt，让 DSH 真产生内容。

| ID | 判据 | 超时 |
|---|---|---|
| **B1** | App 正打开该会话时，新消息**自动出现** | **10s 内必须出现**（客观阈值） |
| **B2** | assistant 流式内容**实时增长**（打字机效应，非一次性出现） | 观察 `streaming` 帧是否逐条反映到 UI |
| **B3** | 会话状态跟随 idle→running→idle | 状态徽标 ≤10s 内变化 |
| **B4** | App 后台再回前台，**能补上**期间新增内容 | 回前台 ≤10s 内补齐 |
| **B5** | 对照组：App **完全退出**后重进，也能拉到最新（证明数据源没问题，问题在实时通道） | ≤10s |

> **B1/B4 的判据来源**：网关侧实测"事件延迟 0ms、持续推送"，故 10s 是**极宽松**阈值；若 App 10s 内仍不更新，即可判定为 App 缺陷而非网络抖动。

## 3. C 组 —— bug3 切换会话后不更新（与 B 同源，单独验）

| ID | 判据 |
|---|---|
| **C1** | 打开 X → 切到 Y → **切回 X**，X 显示**最新内容**（非上次缓存） |
| **C2** | 打开 X → 切到 Y → **Y 期间 X 产生新消息** → 切回 X，**必须看到新消息** |

| **C4** | **切换后旧会话的 WS 订阅是否解除** —— 两个会话同时有事件，验证**不串台**（C4 是 bug3 最可能的实现缺陷点） |

**C4 的客观判据**：订阅 X 与 Y，同时在 X 与 Y 产生消息；切到 Y 后 UI **只应**出现 Y 的事件；若出现 X 的事件内容即为串台。

## 5. 给开发的**可测性建议**（否则 A 组判据无法取证）

A1~A3 需要"App 到底请求了什么"。两个可选方案，任选其一即可让我客观判定：

- **方案 1（推荐，零改动）**：网关侧加一个**只读**请求计数器（如 `GET /rc/v1/_debug/requests?since=<ms>`），返回 `{path, count, lastAt}`。我只读它，不写。
- **方案 2**：App 在 OkHttp 上加一个 `EventListener`，把 `callStart/request` 以 `Log.i("DshHttp", path)` 打出。我用 `adb logcat -s DshHttp` 取证。

无论哪种，我都会给出**请求次数 + 路径 + 时间戳**的表格作为判据，而非主观描述。
