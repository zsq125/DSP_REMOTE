# DSH 手机远程控制 — 架构与接口规范 v1（PM 冻结）

> 本文件是开发 subagent 与测试 subagent 的**唯一共同依据**。接口形状（路径、字段名、类型、语义）一经冻结，任一方不得单方面更改；如需变更必须先回报 PM。

## 0. 目标与范围

- 目标：Android 手机 App 远程**查看并控制** PC 上 DeepSeek Harness（DSH）的任务。
- 范围：列出 PC 上的任务/会话、查看某任务的历史与实时输出、发送指令、中断任务、新建任务、扫码配对、后台保活。
- 不做：文件上传/下载、图片附件、语音、多 PC 管理、账号体系、TLS 证书体系（局域网明文 + token 即可）。

## 1. 组成

```
android-app/            Android 原生 App（Kotlin + Jetpack Compose）
pc-gateway/             PC 端网关（Node.js / DSH Cordis 插件 + patch 文件 + 启动脚本）
tests/                  跨端契约测试与验证脚本
docs/                   本规范与测试报告
```

## 2. PC 端网关（硬约束）

1. 不得修改用户已有的 `~/.dsh/profiles/web/cordis.patch.yml` 或任何 `*.bak-*` 文件。
2. 不得要求重启用户**当前正在运行**的 DSH 实例（本次会话期间它必须保持存活）。
3. 网关必须能独立启动、独立停止、独立测试，且可重复启动（端口固定、有 PID/状态文件）。
4. 必须能列出并读取 PC 上**已有**的 DSH 会话（即 web GUI 里那些任务），并能对其发送提示与中断。
5. 手机侧协议不经 DSH 的 `/api` 浏览器信任栅栏（该栅栏拒绝非 loopback Host）。

**已采用的实现路径**：

```powershell
# 第二个 DSH 实例：复用 web profile 组合（含用户模型凭据与 provider 配置），
# 叠加我们自己的 patch 加载网关插件，端口独立、不开浏览器
dsh --profile web --patch <repo>\pc-gateway\gateway.patch.yml --port 3099 --no-open
```

- 插件包名 `@local/dsh-remote-gateway`，`inject: ['sessionController']`（`list/create/prompt/cancel/page/follow/control`）。
- 插件**自建 `node:http` 服务**监听 `0.0.0.0:8765`（端口可配），不注册到 `ctx.webServer`（避免被 `/api` 信任栅栏与 0.0.0.0 限制牵制）。
- 端口分工：`8765` = 手机侧 App 端口；`3099` = 第二个 DSH 实例自身的 web 端口（只在 PC 本机用，不暴露给手机）。
- 启动脚本 `pc-gateway/start-gateway.ps1`（`.cmd` 包装）：拉起网关实例、打印配对二维码（ASCII）、把 `host/port/token` 写入 `pc-gateway/.state/gateway.json`；配套 `stop-gateway.ps1`。
- 网关 token：首次启动生成 32 位十六进制随机串，持久化到 `pc-gateway/.state/token.txt`，重启不变。

## 3. 接口契约 v1（冻结）

### 3.1 通用

- 编码：UTF-8 JSON。
- 鉴权：HTTP 头 `Authorization: Bearer <token>`；WebSocket 用查询参数 `?token=<token>`。
  鉴权失败 → HTTP 401 / WS 关闭码 4401。
- 免鉴权端点：`GET /rc/v1/ping`。
- 所有响应体都带 `"v": 1` 字段。
- 时间戳统一为 Unix 毫秒整数。
- 错误响应：`{"v":1,"error":{"code":"<code>","message":"<human text>"}}` + 对应 HTTP 状态码。

### 3.2 REST 端点

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/rc/v1/ping` | 否 | 连通性探测 |
| GET | `/rc/v1/status` | 是 | 网关与 DSH 状态 |
| GET | `/rc/v1/sessions` | 是 | 任务列表 |
| GET | `/rc/v1/sessions/{id}/messages` | 是 | 任务历史消息 |
| POST | `/rc/v1/sessions` | 是 | 新建任务 |
| POST | `/rc/v1/sessions/{id}/prompt` | 是 | 发送指令 |
| POST | `/rc/v1/sessions/{id}/cancel` | 是 | 中断当前回合 |
| POST | `/rc/v1/pair/rotate` | 是 | 轮换 token（旧 token 立即失效） |

响应示例（字段名为契约，不得改）：

```jsonc
// GET /rc/v1/ping  (200)
{"v":1,"name":"DESKTOP-XXX","version":"1.0.0","pairRequired":true,"ts":1730000000000}

// GET /rc/v1/status  (200)
{"v":1,"dsh":{"ok":true},"sessions":{"total":12,"running":1},"uptimeMs":12345,"ts":1730000000000}

// GET /rc/v1/sessions?limit=50&cursor=<opaque>  (200)
{"v":1,"items":[{
  "id":"<sessionId>","title":"修复登录超时","status":"running",  // running|idle|unknown
  "createdAt":1730000000000,"updatedAt":1730000000000,
  "cwd":"F:\\project\\x","messageCount":24,"lastMessagePreview":"...",
  "agentAvailable":true
}],"nextCursor":null}

// GET /rc/v1/sessions/{id}/messages?limit=50&before=<seq>  (200)
{"v":1,"items":[{
  "seq":120,"role":"user",           // user|assistant|tool|system
  "text":"跑一下测试","ts":1730000000000,"status":"final",  // final|streaming|failed
  "messageId":"<id 或 null>","requestId":"<id 或 null>"      // 见 §10.2
}],"nextCursor":null}

// POST /rc/v1/sessions/{id}/prompt  body {"text":"...","requestId":"<uuid>"}  (200)
{"v":1,"accepted":true,"messageId":"<id>","sessionId":"<id>"}

// POST /rc/v1/sessions  body {"cwd":null,"title":null}  (200)
{"v":1,"id":"<sessionId>"}

// POST /rc/v1/sessions/{id}/cancel  (200)
{"v":1,"ok":true}
```

约定：
- `prompt` 的 `requestId` 用于幂等：同一 `requestId` 重复提交返回同一 `messageId`，不重复入队。
- 目标会话正被 PC 上其它 DSH 实例写锁持有时返回 409 `session_busy`。
- `messages` 按时间升序返回；`before` 为向前分页游标（返回 `seq` 小于该值的最新一页）。
- 消息 `text` 为纯文本（工具调用折叠为一行摘要 `[tool] <name>` 即可，v1 不要求富结构）。

### 3.3 WebSocket `/rc/v1/stream?token=<token>`

连接后服务端**立即**发送 `hello`。之后为双向 JSON 文本帧。

服务端 → 客户端：

```jsonc
{"v":1,"type":"hello","server":{"name":"DESKTOP-XXX","version":"1.0.0"},"sessions":[{...同 REST 列表项...}]}
{"v":1,"type":"session.event","sessionId":"<id>","event":{
    "kind":"message",                 // message|status|turn
    "role":"assistant","text":"...","seq":121,"ts":1730000000000,
    "status":"streaming",             // streaming|final|failed
    "messageId":"<id 或 null>"}}
{"v":1,"type":"session.status","sessionId":"<id>","status":"running","ts":1730000000000}
{"v":1,"type":"ack","id":"<client id>","ok":true}
{"v":1,"type":"error","id":"<client id 或 null>","code":"session_busy","message":"..."}
{"v":1,"type":"pong","ts":1730000000000}
```

客户端 → 服务端：

```jsonc
{"v":1,"type":"ping","ts":1730000000000}
{"v":1,"type":"subscribe","id":"c1","sessionId":"<id>"}
{"v":1,"type":"unsubscribe","id":"c2","sessionId":"<id>"}
{"v":1,"type":"prompt","id":"c3","sessionId":"<id>","text":"...","requestId":"<uuid>"}
{"v":1,"type":"cancel","id":"c4","sessionId":"<id>"}
```

约定：
- `subscribe` 后该会话的 `session.event`/`session.status` 才推送（`hello` 后默认只推全局 `session.status`）。未订阅会话的 `message` 事件不推。
- 每个客户端消息若带 `id`，服务端必须回 `ack`（成功）或 `error`（失败，带同一 `id`）。
- 服务端在 25s 未收到任何帧时不得主动断开（保活由客户端 ping 驱动，服务端只负责回 pong）。
- 同一 token 允许多客户端并发连接。

### 3.4 配对二维码

PC 端展示的二维码内容为**单行 JSON 文本**：

```json
{"v":1,"name":"DESKTOP-XXX","host":"192.168.1.5","port":8765,"token":"<32hex>","fp":"<8hex>"}
```

- `host` 必须是手机可达的局域网 IPv4；`fp` 为 token 前 8 位，仅用于 UI 展示校验。
- App 同时支持手动输入 `host:port` + token。token 长期有效，仅 token 轮换 / App 数据被清除 / host 变化时才需重新配对。

## 4. Android App 要求

- 包名 `com.deepseek.dshremote`；`minSdk 26`，`targetSdk 34`，`compileSdk 34`。
- 技术栈：Kotlin + Jetpack Compose + OkHttp + Coroutines/Flow + CameraX + ML Kit Barcode
  + DataStore(或 EncryptedSharedPreferences) 存 token。**禁止**引入构建期需 kapt/KSP 的重型注解处理器（Hilt 若导致构建失败则改手动 DI）。
- 页面：配对页（扫码/手输）、任务列表、任务详情（历史 + 实时流 + 输入 + 中断）、设置
  （连接信息、通知保活开关、电池优化白名单入口、厂商自启动引导）。
- 连接状态机必须显式实现 `DISCONNECTED / CONNECTING / CONNECTED / WAITING_FOR_RETRY / BACKING_OFF / DRAINING_QUEUE`，并在 UI 可见。
- 心跳：应用层 ping 间隔 25s，等 pong 超时 10s，超时判定连接失效并重连。
- 重连：初始 500ms，指数退避上限 30s，抖动 0–50%。
- 断线期间用户发出的指令进入本地队列；重连后先按顺序排空队列（DRAINING_QUEUE），逐条等待 `ack` 后才发下一条，再恢复常态。
- 前台服务持有 WS 连接；`startForeground()` 必须在启动后 5s 内调用；通知高优先级、`setOngoing(true)`、不可清除；Android 14 需声明 `foregroundServiceType` 并在 manifest 声明对应权限。
- 网络变化监听（`ConnectivityManager.NetworkCallback`）在 Wi-Fi/蜂窝切换时触发重连。
- 明文 HTTP：需 `android:usesCleartextTraffic` 或 network-security-config 允许局域网明文。

## 7. v1.1 裁定（GAP 决议，PM 裁定，作为契约的一部分）

> 测试方提出 22 项规范缺口。以下为最终裁定：**开发按此实现，测试按此判定**，不得再各自解释。

| GAP | 裁定 |
|---|---|
| 01 | `POST /rc/v1/pair/rotate` 成功 200：`{"v":1,"token":"<新32hex>","fp":"<新token前8位>","ts":<ms>}`。旧 token **立即失效**（新连接必须用新 token）。 |
| 02 | rotate **不断开**已建立的连接；仅影响后续新连接的鉴权。 |
| 03 | `limit` 非整数或不在 `1..200` → 400 `invalid_request`；缺省 50。 |
| 04 | `POST /rc/v1/sessions` 的 `cwd` 非 null 且路径不存在 → 400 `invalid_request`；`null` → 使用网关默认工作目录。 |
| 05 | `prompt` 的 `text` 去首尾空白后为空 → 400 `invalid_request`。 |
| 06 | 校验顺序：**先路径/资源（404）后 body（400）**。`/sessions/{不存在id}/prompt` 无论 body 是否合法都返回 404。 |
| 07 | 对"本网关自己正在 running"的会话发 prompt → **接受并入队**，200 accepted；409 仅表示**跨实例写锁**冲突。 |
| 08 | `cancel` 对 idle 或不存在活动回合的会话 → **幂等 200** `{"v":1,"ok":true}`。 |
| 09 | WS 鉴权失败：**先完成 upgrade，随后立即 `close(4401)`**，不发送任何帧（客户端以 close code 判定）。 |
| 10 | `prompt` 的 `ack` 必须带对账字段：`{"v":1,"type":"ack","id":"<client id>","ok":true,"sessionId":"<id>","requestId":"<uuid>","messageId":"<id>"}`；其他类型 `ack` 至少带 `id`/`ok`。 |
| 11 | 未知 `type` → `error` 帧 `code:"invalid_request"`，可解析则带同一 `id`，**不断开连接**。 |
| 12 | `v != 1` → `error` 帧 `code:"invalid_request"`，不断开连接。 |
| 13 | `ack`/`error` **只发给请求发起的那条连接**，不广播。 |
| 14 | 客户端"等 pong"计时**只由 `pong` 帧复位**，其他入站帧不复位；服务端不主动超时断开。 |
| 15 | 队列重试：`session_busy` → 每 2s 重试、最多 3 次，仍失败则标记失败；其他 4xx → 直接标记失败不重试；网络断开 → 保持待发。 |
| 16 | 本地待发队列上限 **200 条**，满则拒绝入队并在 UI 明确提示（不静默丢弃）。 |
| 17 | 待发队列**必须持久化**（DataStore/文件/SQLite 均可）；App 进程被杀后重启必须仍能排空。 |
| 18 | DSH 内层不可用：`GET /rc/v1/status` 仍 200（`dsh.ok=false`）；其余依赖 DSH 的端点返回 **503 `dsh_unavailable`**。 |
| 19 | `messages`：items 按 `seq` **升序**；`before` = 只取 `seq < before` 的最新 `limit` 条；`nextCursor` = 本页最小 `seq`（无更早则 null）。 |
| 20 | 启动脚本路径冻结：`pc-gateway/start-gateway.ps1`、`pc-gateway/stop-gateway.ps1`；状态文件 `pc-gateway/.state/gateway.json`（字段 `host,port,token,fp,pid,startedAt`）与 `pc-gateway/.state/token.txt`。 |
| 21 | `sessions`：按 `updatedAt` **降序**；`cursor` 为不透明字符串（建议 base64(`updatedAt|id`)）；`nextCursor=null` 表示结束。 |
| 22 | 允许**仅测试门控**的 409 钩子：环境变量 `DSH_RC_TEST_HOOKS=1` 时额外注册 `POST /rc/v1/_test/busy/{id}`（令该会话下一次 prompt 返回一次 409）；默认**不注册**该路由。真实 409 路径（对正被 3080 实例写锁持有的会话发 prompt）同样必须可用。 |

**错误码表（完整）**：`unauthorized`(401)、`invalid_request`(400)、`not_found`(404)、`session_busy`(409)、`dsh_unavailable`(503)、`internal`(500)。

## 8. v1.2 追加：局域网地址选择（P0 可用性）

**问题**：原实现 `lanIpv4()` 取「第一个非 loopback 的 IPv4」，在本机枚举顺序恰好撞上 **VMware VMnet8 `192.168.125.1`**，手机无法访问该网段 ⇒ 扫码后必然连不上。

本机真实网络（实测）：

| 接口 | IPv4 | 性质 | 手机可达 |
|---|---|---|---|
| **WLAN** | **192.168.2.27** | 真实无线，**默认路由所在**（网关 192.168.2.1），网络类别 Public | ✅ |
| VMware Network Adapter VMnet1 | 192.168.211.1 | 虚拟 | ❌ |
| VMware Network Adapter VMnet8 | 192.168.125.1 | 虚拟 | ❌ |
| 以太网 | 169.254.185.79 | 未连接（link-local） | ❌ |

**强制要求**：

1. `host` 选择顺序：排除 loopback → 排除 `169.254.*` → **排除虚拟网卡**（接口名匹配 `vmware|virtualbox|vbox|hyper-v|vethernet|loopback|docker|wsl|tap|npcap|bluetooth|zerotier|tailscale|hamachi|radmin|sandbox`，忽略大小写）→ 其余取优先级最高者（有默认路由的物理网卡优先）。
2. 启动时**必须打印全部候选地址**并标明选中项与"为什么选它"。
3. `start-gateway.ps1` / `.cmd` **必须支持 `-LanHost <ip>`** 强制覆盖（多网卡用户自选）。
4. 二维码与 `.state/gateway.json` 的 `host` 使用最终选中值。
5. App 侧必须支持手动输入 `host:port` + token（不能只依赖扫码），作为多网卡/选错时的兜底。

**防火墙结论（无需额外动作，但文档要写）**：本机已有入站 Allow 规则 `Node.js JavaScript Runtime` → `E:\system\nodejs\node.exe`（TCP **Any** 端口，Public 类别），而 WLAN 恰好是 Public，网关进程又跑在同一 `node.exe` 上 ⇒ **无需用户手动放行**。若换机器没有该规则，则需放行 `node.exe` 或 TCP 8765。

**验证边界**：本机无法验证"手机是否真的能连"（防火墙对 loopback 访问本机 IP 不生效），该项必须由用户真机验证；测试报告须如实标注。

## 9. v1.3 追加：门控钩子覆盖 WS、messages 落库语义、事件风暴、脚本编码

### 9.1 门控钩子必须同时覆盖 REST 与 WS（P0）

`DSH_RC_TEST_HOOKS=1` 注入的写锁（`session_busy`）行为**必须对 REST 与 WS 两条通道一致**：

- `POST /rc/v1/sessions/{id}/prompt` 遇写锁 → 409 `session_busy`；
- **WS `prompt` 帧遇写锁 → 回 `error` 帧**（带同一 `id`、`code:"session_busy"`），**绝不允许回 `ack ok:true`**。

理由：App 在 `DRAINING_QUEUE` 排空时依赖 ack 决定出队。若 WS 通道误 ack，该指令会被判为"已发送"而**静默丢失**。

### 9.2 `/messages` 落库时机与 `waitRequestId`（正式纳入契约）

- **不要求** `prompt` 被接受后 `GET /messages` 立即可见。内层架构为：prompt 先入 inbox 队列，assistant 回合结束后才持久化。
- 因此将网关已实现的可选查询参数正式纳入契约：`GET /rc/v1/sessions/{id}/messages?waitRequestId=<requestId>`
  - 语义：轮询直到该 `requestId` 对应的 durable user 消息出现，**最长 12s**；
  - 超时：返回当前已有内容，HTTP **仍为 200**（不报错、不返回 4xx/5xx）；
  - 不传该参数时保持普通语义。

### 9.3 事件风暴：服务端不节流，App 侧必须节流

实测：一次 prompt 可产生约 **180 帧** `session.event`（reasoning / tool-call / tool 逐条推送）。

- **服务端保持全量推送、不丢弃、不节流**（数据完整性优先，协议不变）；
- **App 侧硬性要求**：① UI 渲染必须以 **≤100ms 批次合并**（不要一帧一重组）；② 消息列表必须使用虚拟滚动（LazyColumn）；③ reasoning 类帧**默认折叠**，可展开。

### 9.4 已定案：`pc-gateway/*.ps1` 一律纯 ASCII

**根因**：脚本含中文时，Windows PowerShell 5.1 按系统 ANSI(GBK) 解码**无 BOM** 文件；某中文字符的 UTF-8 末字节会与相邻的 ASCII `'` 组成一个 GBK 双字节字符，**吃掉右引号**，导致后续字符串未闭合、报 `Unexpected token`。（实例：`'手机侧网关端口'` 被 GBK 解读后末字节吃掉右引号。）`ParseFile` 与运行时 tokenizer 对同一字节序列处理不一致，**不能把 `ParseFile` 当唯一判据**。

**定案要求**：

1. `pc-gateway/*.ps1` **一律纯 ASCII**（`nonAscii = 0`）；中文说明移入 `README.md` 与文件头英文注释；
2. 编码 **UTF-8 无 BOM**、**CRLF** 行尾；
3. 任何改动后必须**用 PowerShell 5.1 实际起停一次**验证，而不是只看解析器结果；
4. 文件头需注明"为什么必须 ASCII"，防止后人加回中文注释。

**同时修复的关联缺陷**：`start-gateway.ps1` 曾自行枚举网卡计算展示用地址，**绕过了插件内的 v1.2 选择逻辑**，导致二维码仍打印 `192.168.125.1`。现改为读取插件写入的 `.state/runtime.json` 作为**唯一权威来源**。

### 9.5 测试用干跑钩子（控消耗）

`DSH_RC_TEST_HOOKS=1` 时额外提供 `POST /rc/v1/_test/echo-prompt`：接受 prompt 但**不投递给模型**，仅返回 `{accepted,messageId,sessionId}` 并参与幂等登记；默认**不注册**。测试的字段/幂等类用例应优先使用它，以避免真实模型调用与 token 消耗。

## 10. v1.4 追加：分页游标与 prompt 对账键

### 10.1 `sessions` 的 `nextCursor` 必须可用（P0）

**实测缺陷**：`?limit=50/100/缺省` 均只回 50/100 条且 `nextCursor=null`（实际共 129 个会话）；只有 `limit ≥ 总数` 才拿全 ⇒ App 任务列表只能看到最近 50 个会话。

**裁定**：

1. `limit` 缺省 50，范围 `1..200`（越界仍按 GAP-03 返回 400）；
2. **只要还存在未返回项，`nextCursor` 就必须为非 null** 的可用于继续翻页的游标；
3. 客户端按 `updatedAt` **降序** + `cursor` 逐页拉取，**必须能在有限页内取到全部会话，且无重复、无遗漏**；
4. 不传 `limit` 时同样必须支持翻页取全（不得因为用了默认值就无法继续）。

### 10.2 prompt 对账键：`messageId` 与 `requestId` 的分工（P0）

**实测缺陷**：`prompt` 回执 `messageId=2900e8bd-…`，但 `GET /messages?waitRequestId=<rid>` 中该 id **出现 0 次**；落库的 user 行使用 DSH 自己的 durable id。

**根因（属架构事实，非实现错误）**：内层 `prompt()` 只返回 `{accepted:true}`，且消息要等 assistant 回合结束才持久化 ⇒ 网关在**受理时不可能知道** durable id。

**裁定**：

1. **`messageId` 语义保持不变** = **网关受理 id**：立即可用；同一 `(sessionId, requestId)` 幂等重放时**稳定不变**。用途**仅限**同会话内的幂等重放判定，**不用于跨进程/崩溃恢复的持久对账**。
2. **`GET /messages` 的 `user` 行必须新增 `requestId` 字段**（值取自 durable `source.rpcId`，可为 `null`）。**这是崩溃恢复对账的权威键。**
3. `?waitRequestId=` 语义不变（§9.2）。
4. **App 侧对账设计**：乐观上屏用本地待发队列项自带的 `requestId`（App 生成，端到端稳定）；崩溃恢复用 `requestId` 与 `/messages` 返回的 `requestId` 对齐；`messageId` **仅**用于同一次发送的幂等重试判定。

### 10.3 一条 prompt 必须恰好产生 1 条 durable user 行（P2）

一次 `prompt`（含幂等重放）在 `/messages` 中应恰好出现 **1** 条 durable `role:"user"` 行。
