## 1. 自动化分层计划

| 层 | 覆盖 | 载体 | 需真机 |
|---|---|---|---|
| **L1 JVM 单测** | 退避/抖动、状态机迁移、pong 超时、队列顺序与逐条 ack、断连 n 次不丢、二维码解析、token 指纹、分页 cursor、host 网段校验 | `android-app/app/src/test/...`（纯 JUnit/kotlin-test，**禁止**需 kapt/KSP 的依赖） | 否 |
| **L2 Robolectric** | `startForeground()` 5s 时限、通知 ongoing/高优先级、manifest `foregroundServiceType`/权限、`NetworkCallback` 注册与切换触发重连 | 同上（robolectric + `shadowOf`） | 否 |
| **L3 跨端 E2E** | 规范 §5 第 3、4 条：全部 REST 端点 / WS 消息 / 错误路径 / 幂等 / 并发 / 订阅语义；配对→列表→订阅→发指令→流式事件→中断→队列重发全程真实网络 | `tests/e2e/`（JVM 客户端，**必须**打真实 `127.0.0.1:8765`，不得用 MockWebServer） | 否 |
| **L4 静态校验** | `assembleDebug` / `testDebugUnitTest` / `lintDebug` / `aapt2 dump badging` / `apksigner verify` / 危险权限审查 | `tests/build/verify-apk.ps1` 等 | 否 |
| **L5 人工审查** | 电池优化入口、厂商自启动引导 UX、前台服务实际保活效果 | 代码审查 + 截图 | 部分 |
| **L6 真机项** | 息屏保活、Doze 下 WS 不掉、通知不可清除、扫码相机实际识别、系统设置跳转、厂商白名单 | 手工用例（见 §7） | **是** |

**判定原则**：L1–L4 全部自动化且必须全绿，才允许把"App 可完美运行"写进验收；L6 只能由用户签字。

## 2. 协议契约用例（规范 §3）

### 2.1 通用规则

- **PROTO-G01**·P0 网关启动 → 无 Authorization 头 GET `/rc/v1/ping` ⇒ 200 且体含 `"v":1`
- **PROTO-G02**·P0 同上 ⇒ 含 `name/version/pairRequired/ts`；`ts` 为**整数毫秒**（`ts % 1 === 0` 且 `> 1.7e12`；PowerShell `.ts.GetType().Name` 须为 `Int64`）
- **PROTO-G03**·P1 同上 ⇒ `name` 与宿主机名/`.state/gateway.json` 一致
- **PROTO-G04/G05/G06**·P0 同上 → 无 token／`Bearer deadbeef`／`Basic xxx` 调 `/rc/v1/status` ⇒ 401 `error.code=="unauthorized"`、`message` 非空，**不得 500**
- **PROTO-G07**·P0 同上 → 遍历所有错误路径 ⇒ 一律 `{"v":1,"error":{"code","message"}}`，`message` 非空
- **PROTO-G08**·P0 同上 → 对**每个** 2xx 响应断言 `"v"===1` ⇒ 全部通过
- **PROTO-G09**·P0 已 rotate 一次 → 旧 token 调 `/status`；新 token 调 ⇒ 旧 401、新 200
- **PROTO-G10**·P0 网关重启前后 → 比较 `.state/token.txt` ⇒ 重启后不变且满足 `^[0-9a-f]{32}$`
- **PROTO-G11/G12**·P2 网关启动 → `GET /rc/v1/nope`／`DELETE /rc/v1/sessions` ⇒ 404 `not_found`（未知路径）／405 或 404；**均不得 500 泄漏栈**
- **PROTO-G13**·P1 同上 → prompt 文本含中文+emoji+换行 ⇒ 落库与回读一致、无乱码
- **PROTO-G14**·P2 同上 → prompt 发非 JSON 体 ⇒ 400 `invalid_request`，不得 500

### 2.2 `GET /rc/v1/status`

- **REST-S01**·P0 网关运行且 DSH runtime 在线 → 带 token GET ⇒ 200；`v==1`；`dsh.ok===true`；`sessions.total` 整数 ≥0；`uptimeMs` 整数且单调增长（间隔 2s 两次采样）；`ts` 整数
- **REST-S02**·P0 PC 上有 N 个会话 → 对比 `status.sessions.total`、`/sessions.items.length` 与 web GUI ⇒ 一致（分页时 total 为全量而非本页）
- **REST-S03**·P1 有正在跑的回合 → 对比 `sessions.running` ⇒ 与实际 running 数一致

### 2.3 `GET /rc/v1/sessions`（任务列表）

- **REST-L01**·P0 PC 有 ≥3 会话 → GET ⇒ 每个 item 含 `id,title,status,createdAt,updatedAt,cwd,messageCount,lastMessagePreview,agentAvailable`，**缺一即失败**
- **REST-L02/L03**·P0 同上 ⇒ `status` ∈ {running,idle,unknown} 无越界；`createdAt/updatedAt` 为整数毫秒且 `updatedAt>=createdAt`
- **REST-L04**·P0 会话数 >3 → `?limit=3` ⇒ `items.length===3` 且 `nextCursor` 为非 null 字符串
- **REST-L05**·P0 同上 → 用 `nextCursor` 循环取全量 ⇒ 取尽后 `nextCursor===null`；全程 id 无重复、无遗漏（set 比对）
- **REST-L06**·P1 同上 → `?limit=0/-5/abc` ⇒ 400 `invalid_request`（裁定 GAP-03）
- **REST-L07/L08**·P2 同上 → `?cursor=@@bogus@@`／`?limit=100000` ⇒ 400 或降级首页／夹到上限并 200；**均不得 500、不得 OOM**
- **REST-L09**·P1 干净网关（无会话）→ GET ⇒ `items===[]`、`nextCursor===null`
- **REST-L10/L11**·P1 存在本地会话 → 检查 `cwd` 与 `lastMessagePreview` ⇒ cwd 为 Windows 路径形态且非空或 null（不抛错）；preview 非空字符串、含换行时已截断为单行（不含 `\n`）
- **REST-L12**·P0 DSH web GUI 可见任务 → 网关返回 id 与 GUI 任务逐一对应 ⇒ 能对应到用户已有任务（规范 §2 第 4 条）

### 2.4 `GET /rc/v1/sessions/{id}/messages`

- **REST-M01/M02**·P0 有 ≥1 条消息的会话 → GET ⇒ 每 item 含 `seq,role,text,ts,status,messageId,requestId`；`role`∈{user,assistant,tool,system}；`status`∈{final,streaming,failed}；`seq` 严格递增
- **REST-M03/M04**·P0 会话有 ≥10 条消息 → `?limit=3` 连续翻页到最后一页 ⇒ 每次返回 `seq < before` 的最新一页；三页拼接无重复无遗漏；到底 `nextCursor===null`
- **REST-M05**·P0 — → `GET /rc/v1/sessions/sess_does_not_exist/messages` ⇒ 404 `not_found`
- **REST-M06**·P1 新建空会话 → GET ⇒ `items===[]`、`nextCursor===null`
- **REST-M07**·P1 会话含工具调用 → 检查 tool 消息 `text` ⇒ 形如 `[tool] <name>`、单行（正则 `^\[tool\] \S+`）
- **REST-M08**·P2 含 streaming 消息 → 检查 ⇒ `messageId` 允许 `null` 但**不得缺键**
- **REST-M09**·P2 同上 → `?before=abc` ⇒ 400 `invalid_request`，不得 500

### 2.5 `POST /rc/v1/sessions`（新建任务）

- **REST-C01**·P0 网关运行 → POST `{}` ⇒ 200 `{"v":1,"id":"<非空>"}`，随后出现在列表
- **REST-C02**·P1 同上 → POST `{"cwd":"F:\\project\\x","title":"手工测试"}` ⇒ 200 且列表项 `title`/`cwd` 与入参一致
- **REST-C03/C04/C05**·P1 同上 → POST `{"cwd":"Z:\\不存在\\目录"}`／`{"cwd":123}`／`{"foo":"bar"}` ⇒ 400 `invalid_request`（GAP-04）／400／200 忽略或 400；**均不得 500**
- **REST-C06**·P0 同上 → 无 Authorization ⇒ 401 `unauthorized`

### 2.6 `POST /rc/v1/sessions/{id}/prompt`（发送指令）

> 字段/幂等类用例优先用 `_test/echo-prompt` 干跑钩子（§2.9b），避免真实模型调用与 token 消耗。

- **REST-P01**·P0 会话 idle → POST `{"text":"跑一下测试","requestId":"<uuid>"}` ⇒ 200；`accepted===true`；`messageId` 非空；`sessionId` 等于路径 id；该消息出现在 `/messages` 且 `role=user`
- **REST-P02/P03**·P0 同上 → 同一 requestId 连发 3 次 ⇒ 3 次返回**同一** `messageId`、`/messages` 中该 text 只出现 1 次；两个不同 requestId 同文本 ⇒ 两个不同 messageId、落 2 条
- **REST-P04/P05/P06/P07**·P0 同上 → 缺 `text`／`text` 非字符串／`text` 空白／缺 `requestId` ⇒ 400 `invalid_request`（P06 见 GAP-05）
- **REST-P08**·P0 同上 → POST `/sessions/nope/prompt` ⇒ **404 优先于 400**（GAP-06）
- **REST-P09/P10**·P0 目标会话被其它 DSH 实例写锁持有 → POST 合法 prompt ⇒ 409 `session_busy`、`message` 非空（用门控钩子确定性构造，禁止干扰用户会话）；解锁后重试同 requestId ⇒ 200 且**此时才真正入队**
- **REST-P11**·P1 会话正在跑 → POST prompt ⇒ 200 accepted（GAP-07：本网关自己的 running 会话接受并入队），不得 500
- **REST-P12**·P2 同上 → 1MB 文本 ⇒ 不崩溃；200 或 400

### 2.7 `POST /rc/v1/sessions/{id}/cancel`（中断）

- **REST-X01**·P0 会话正在跑长任务 → POST cancel ⇒ 200 `{"v":1,"ok":true}`；该回合出现 `status=="failed"` 或会话转 idle；之后仍可 prompt
- **REST-X02/X05**·P1 会话 idle／已取消 → POST cancel（连按 3 次） ⇒ 200 `ok:true` 幂等（GAP-08），无异常、无重复事件，不得 500
- **REST-X03/X04**·P0 — → POST `/sessions/nope/cancel`／无 Authorization ⇒ 404 `not_found`／401

### 2.8 `POST /rc/v1/pair/rotate`

- **REST-R01/R01b**·P0 网关运行、旧 token 已知 → POST rotate ⇒ 200 且 body **恰含** `v=1`、`token`(新 32hex)、`fp`(=新 token 前 8 位)、`ts`(整数 ms)，不得缺键；新 ≠ 旧且 `.state/token.txt` 已同步
- **REST-R02/R03**·P0 同上 → 用旧 token／新 token 请求 ⇒ 旧 401 `unauthorized`（**立即**，无需重启）；新 200，且 WS 用新 token 可连并收 hello
- **REST-R04**·P0 rotate 后重启网关 → 用新 token ⇒ 200（token 重启不变）
- **REST-R05**·P0 — → 无 Authorization ⇒ 401
- **REST-R06**·P0 先用旧 token 建立 WS 并保持 OPEN → rotate 后继续收发 60s ⇒ **旧 WS 仍 OPEN**（GAP-02：不得 close 4401）；ping/pong 正常、subscribe 仍 ack、事件继续推
- **REST-R07**·P0 rotate 后 → 新建 WS 用旧 token ⇒ 握手后立即 close **4401**（GAP-09）
- **REST-R08**·P0 连做 2 次 rotate ⇒ 每次 `fp == token[:8]`；三次 token 两两不同；`ts` 单调不减

### 2.9 WebSocket `/rc/v1/stream?token=`

> 判定口径：鉴权失败**只按 close code 4401** 判定，不按 HTTP 状态码。

- **WS-01**·P0 网关运行 → 连 `ws://host:8765/rc/v1/stream?token=<tok>` ⇒ 握手成功；**立即**收到 `type=="hello"`
- **WS-02/WS-02b/WS-03**·P0 同上 → `?token=`（空）／完全无 query／`?token=deadbeef` ⇒ upgrade 后**不发送任何帧**，立即 close code **4401**；口径固定为"零帧 + close 4401"
- **WS-04**·P0 已连接 → 检查 hello ⇒ `v==1`；`server.name/version` 存在；`sessions` 为数组且元素字段同 REST 列表项
- **WS-05**·P0 已连接 → 发 `{"type":"ping","ts":<now>}` ⇒ ≤10s 内收到 `pong`，其 `ts` 为整数毫秒
- **WS-06**·P0 已连接但不发 ping → 静置 30s ⇒ 连接仍 OPEN（服务端不主动断开）
- **WS-07**·P0 已连接 → 发 `subscribe id=c1 sessionId=<id>` ⇒ 收到 `{"type":"ack","id":"c1","ok":true}`，**id 完全一致**
- **WS-08**·P0 同上 → 订阅不存在的 sessionId ⇒ 收到 `error` 且 `id=="c1"`、`code` 非空
- **WS-09**·P0 两会话 A、B，只订阅 A → 在 B 上产生新消息 ⇒ 客户端**收不到** B 的 `session.event` kind=message
- **WS-10**·P0 已订阅 A → 在 A 上 prompt 并产生 assistant 输出 ⇒ 收到 `session.event`，`event.kind=="message"`，含 `role/text/seq/ts/status/messageId`；`seq` 与 REST `/messages` 对应行一致
- **WS-11/WS-12**·P0 未订阅任何会话 → 任一会话状态变化 ⇒ 收到全局 `session.status`，字段 `v==1,type=="session.status",sessionId,status∈{running,idle,unknown},ts` 整数
- **WS-13**·P0 同 WS-10 → 检查 ⇒ `v,type=="session.event",sessionId,event{kind∈{message,status,turn},role,text,seq,ts,status,messageId}` 全部存在
- **WS-14**·P0 订阅 A 并让 A 跑长任务 → 观察序列 ⇒ 出现 `streaming` 消息，最终同一 seq（或 messageId）出现 `final`；顺序单调
- **WS-15**·P0 已订阅 A → 发 `unsubscribe id=c2 sessionId=A` ⇒ ack id=c2；随后 A 的 message 事件不再推（status 仍全局推）
- **WS-16**·P0 已连接 → 发 `prompt id=c3` ⇒ ack `id=="c3"`、`ok===true`，且**必含** `sessionId`(==A)、`requestId`(=所发 uuid)、`messageId`(非空)；随后 messages 出现该条（GAP-10）
- **WS-17**·P0 同上 → 同一 requestId 发两次（id=c3/c5） ⇒ 两条 ack 的 `requestId` 都等于该 uuid；**`messageId` 相同**（只入队 1 条）；`/messages` 中该 text 只出现 1 次
- **WS-18**·P0 造 session_busy 锁 → 发 prompt ⇒ `error`，`id` 为该客户端 id，`code=="session_busy"`（**绝不允许回 ack ok:true**）
- **WS-19**·P1 已连接 → 发缺 `text` 的 prompt ⇒ `error`，`id` 一致，`code=="invalid_request"`
- **WS-20/WS-31**·P0 A 正在跑 → 发 `cancel id=c4` ⇒ ack 含 `id`/`ok`；会话转 idle 或消息 status=failed
- **WS-21**·P1 已连接 → 对不存在会话 cancel ⇒ `error`、`code=="not_found"`、`id` 一致
- **WS-22/WS-23/WS-33**·P2 已连接 → 发未知 `type`／无 `v` 的 ping／`{"v":2,...}` ⇒ 回 `error`（未知 type 为 `invalid_request`，带同一 `id`）；**不断开、不崩溃、不影响后续帧**
- **WS-24/WS-25**·P2 已连接 → 发 `not json`／二进制帧 ⇒ 服务端不崩溃，后续帧仍能 ack
- **WS-26**·P0 网关运行 → 同时建 3 条 WS（同 token）都订阅 A ⇒ 三条都收 hello；A 的一条消息三者都收到；各自 ack 独立、id 空间互不干扰
- **WS-27**·P1 三条 WS → 客户端1 发 prompt id=c3 ⇒ 只有该连接收到 ack c3，另两条不收到（GAP-13）
- **WS-28/WS-29**·P1 三条 WS → 强杀其中一条 ⇒ 其余两条仍 OPEN 且继续收事件；交替发 ping/subscribe/prompt ⇒ 回帧类型不混淆（pong 不带 id、ack 不带 ts）
- **WS-30**·P2 已连接 → 发 512KB text 的 prompt ⇒ 正常处理或明确 error，不崩溃/不断连
- **WS-32**·P1 用测试钩子停内层 DSH → 发 subscribe ⇒ `error`，`code=="dsh_unavailable"`

### 2.9b 测试门控钩子（仅 `DSH_RC_TEST_HOOKS=1` 时注册）

$env:DSH_RC_TEST_HOOKS=0; .\pc-gateway\start-gateway.ps1   # 默认：钩子必须 404

- **HOOK-01**·**P0** 网关以**默认**环境启动 → POST `/rc/v1/_test/busy/<id>`（即使带合法 token） ⇒ **404 not_found**（未注册）；不得 200/409/500

- **HOOK-03**·P0 以 `DSH_RC_TEST_HOOKS=1` 启动 → POST `/_test/busy/<真实id>` ⇒ 200（响应体形状非契约）
- **HOOK-04/HOOK-05**·**P0** 已 HOOK-03 → REST POST `/sessions/<id>/prompt` 合法体 ⇒ **409** `session_busy`；WS 发 prompt 帧 ⇒ `error`，`id` 为该客户端 id、`code=="session_busy"`
- **HOOK-06**·P0 已 HOOK-03 → 解除 busy 后重试 prompt ⇒ 200 accepted，消息真正入队（证明 409 时未入队）
- **HOOK-07**·P1 默认启动 → 无 Authorization POST 钩子路径 ⇒ 401 或 404，**不得** 200
- **HOOK-08**·P1 全程使用钩子后 → 检查 `.state/` ⇒ 钩子状态不落盘到 `gateway.json`/`token.txt`

### 2.10 配对二维码（§3.4）

- **PAIR-01**·P0 网关启动 → 读 `.state/gateway.json` 与终端 ASCII 二维码 ⇒ 单行 JSON 六键齐全 `v,name,host,port,token,fp`；`token` 32 位 hex
- **PAIR-02**·P0 手机与 PC 同局域网 → 检查 `host` ⇒ 手机可达的局域网 IPv4（非 127.0.0.1、非 0.0.0.0、非公网）；PC 侧先自证非回环，**真机项**
- **PAIR-03/PAIR-04**·P0/P1 同上 → 比对 `fp` 与 `token[:8]` ⇒ 完全相等；输出为单行文本（不含 `\n`）
- **PAIR-05**·P1 网关运行 → 检查 `.state/gateway.json` ⇒ 含 `host/port/token`，字段名与实现一致

## 3. App 连接可靠性用例（规范 §4，默认 L1 单测）

### 3.1 状态机六态迁移

> 判定口径：状态必须是**显式枚举**且在 UI 可见；`when` 必须 exhaustive（不得有 default 吞掉未知态）。

- **SM-01**·P0 冷启动 → 读状态 ⇒ `DISCONNECTED`；UI 显示"未连接"
- **SM-02**·P0 冷启动+已配对 → 触发连接 ⇒ `CONNECTING`
- **SM-03**·P0 网关可达 → 收到 `hello` ⇒ `CONNECTED`；解析 hello.sessions（FakeSocket 喂 hello）
- **SM-04/SM-05**·P0/P1 网关不可达（端口关闭）／hang（接受连接不回 hello） → 连接被拒／等 connectTimeout ⇒ `WAITING_FOR_RETRY`，不永久卡 CONNECTING
- **SM-06/SM-07**·P0 第 1 次重连 → 等待退避窗口 ⇒ `BACKING_OFF`（时长 = 退避计算值）；退避到期 ⇒ 自动转回 `CONNECTING` 并发起重连
- **SM-08**·P0 WS 被对端关闭 → 收到 close 帧 ⇒ `WAITING_FOR_RETRY`
- **SM-09**·P0 已连接 → 用户点"断开连接" ⇒ `DISCONNECTED`，**不再重连**
- **SM-10/SM-11/SM-12**·P0/P1 断线期间有 ≥2 条排队指令（无排队） → 重连成功并收到 hello ⇒ `DRAINING_QUEUE` 且排空前不得进 CONNECTED；最后一条收到 ack ⇒ 转 `CONNECTED`；无排队时**直接** `CONNECTED`，不短暂出现 DRAINING
- **SM-13**·P0 排空第 1 条时断开 ⇒ 已 ack 的**不重复补发**；未 ack 的留在队列；回到 `WAITING_FOR_RETRY`
- **SM-14**·P0 综合场景 → 代码审查+单测 ⇒ 6 个枚举值全部有定义且有 UI 映射
- **SM-15**·P1 手工切换状态 → 截图 ⇒ 每个状态在列表/设置页有可见文案（**需用户真机配合**）

### 3.2 心跳与超时

- **HB-01/HB-02**·P0 假 socket 记录出帧 → 连接后不发任何客户端消息 ⇒ **25s±1s** 发出首个 `ping`；虚拟时间推进 100s ⇒ 每 25s 一次、共约 4 次（±1）
- **HB-03**·P0 假 socket 吞掉 pong → 发 ping 后不回 pong ⇒ **10s±0.5s** 判定失效并进入 `WAITING_FOR_RETRY`
- **HB-04/HB-05**·P0/P1 假 socket 正常回 pong（只回 ack 不回 pong） → 连续 5 个周期 ⇒ 不触发重连、计时器每周期复位；只回 ack 时仍按 10s 判超时（GAP-14：只认 pong）
- **HB-06**·P1 处于 DRAINING/BACKING_OFF → 虚拟时间推进 60s ⇒ 非 CONNECTED 态不发 ping

### 3.3 重连退避与抖动（可注入随机源）

- **BK-01**·P0 第一次重连 ⇒ delay ∈ **[500,750]ms**（500 + 0~50% 抖动），100 次采样
- **BK-02**·P0 连续失败 1..6 次 ⇒ base = 500·2^(n-1)（500/1000/2000/4000/8000/16000）；每次实际值 ∈ [base, 1.5·base]
- **BK-03**·P0 失败 20 次 ⇒ base 封顶 30000ms；实际 ∈ [30000,45000]ms，**永不 >45s**
- **BK-04/BK-05/BK-06**·P0/P1 注入随机源 → 返回 0.0／0.5／默认随机 ⇒ delay == base（下界可达）／delay == 1.5·base（≤45s）／采样 200 次不同 delay ≥5 种（确证有抖动）
- **BK-07**·P0 已退避到 10 次 → 连接成功一次 ⇒ 下次失败重连回到 500ms 基准
- **BK-08**·P0 已连接 → 手动断开后虚拟时间推进 120s ⇒ 无任何重连尝试

### 3.4 断线队列与排空（规范 §4 核心）

- **Q-01/Q-02**·P0 `DISCONNECTED`（`CONNECTED`） → 用户发指令 ⇒ 进入本地队列、UI 显示"待发送"、不丢弃；在线时直接发出、不经队列
- **Q-03**·P0 断线期间排 A,B,C → 重连 ⇒ 发出顺序严格 A→B→C
- **Q-04/Q-05**·P0 同上 → A 的 ack 迟到／乱序返回 ack(c2),ack(c1) ⇒ B **必须等 ack(id=A) 到达后**才发出
- **Q-06**·P0 队列首条返回 error ⇒ 该条移出队列并记录失败，继续发下一条，不卡死（重试规则见 GAP-15）
- **Q-07**·P0 发出 A 未收 ack 时断开 → 重连后 ⇒ A 重发一次；不重复发送已 ack 的条目
- **Q-08**·P0 断线重连多次 → 检查补发指令 ⇒ 同一逻辑指令在所有重发中 **requestId 相同**
- **Q-09**·P0 模拟连续 10 次断连、期间入队 10 条 → 恢复后 ⇒ 10 条全部送达，顺序与入队序一致，无丢失无重复
- **Q-10**·P2 长断线 → 入队 500 条 ⇒ 有上限保护（GAP-16：200 条）并明确提示，不得 OOM
- **Q-11**·P1 进程被杀 → 重启 App ⇒ 队列持久化（GAP-17）后仍能排空；至少不静默丢失且有提示（真机项）

### 3.5 端到端跨端契约（真实网关 + Kotlin/JVM 客户端）

- **E2E-01**·P0 网关真实运行 → 配对（读二维码 JSON）→ GET /sessions → WS subscribe → prompt → 收 streaming/final 事件 → cancel ⇒ 全程真实 HTTP/WS 无 mock；事件 text 与 REST `/messages` 对拍一致
- **E2E-02**·P0 同上 → 用可控代理/防火墙规则掐断 WS 3 次，每次恢复后发指令 ⇒ 3 次均自动重连，指令不丢
- **E2E-03**·P0 同上 → 断线期间入队 3 条 → 恢复 ⇒ 观察到 `DRAINING_QUEUE` → 逐条 ack → `CONNECTED`
- **E2E-04**·P1 同上 → 停/启网关（**不得碰 PID 7072**） ⇒ App 退出重连循环；token 不变
- **E2E-05/E2E-06**·P0 同上 → 2 个 JVM 客户端同时连 ⇒ 各自收全事件互不干扰；跑一个多轮对话 ⇒ WS 收齐所有 message，`/messages` 全量拉取后按 seq 对拍集合相等

### 11.1 缺陷用例（修复前必须 FAIL）

- **CONN-D1**·**P0** 配对信息刚提交、DataStore 尚未落盘 → 服务先启动读到 null 早退；随后 `completePairing` 落盘并 `notifyPairingSaved()` ⇒ **必须补建 WS**，早退不得成为终局
- **CONN-D2**·**P0** 服务已启动但当时未配对（早退）→ 随后配对完成再次 `start(context)` ⇒ **必须重试并建立 WS**；`onStartCommand` 的 `if (!started)` 不得吞掉后续重试
- **CONN-D3**·**P0** 磁盘上已有配对信息 → 冷启动/重启 App（**不经过配对页**） ⇒ App 必须自动启动 ConnectionService 并恢复长连接
- **CONN-D4**·**P1** 真实连接已建立（`CONNECTED`）→ 停留在**任务列表页** ⇒ 列表页也必须订阅并显示真实状态

### 11.2 防回归守卫用例（必须始终 PASS）

- **CONN-K1**·P0 已配对+服务启动 → 走标准启动路径 ⇒ 建立**恰好 1 条** WS 连接
- **CONN-K2**·P0 未配对+服务启动 ⇒ **不建连、不崩溃**（早退是合法路径，不得改成抛异常或死循环）
- **CONN-K3**·P0 已配对 → 连续多次 `start()` ⇒ **不得重复建连**（修 D2 时最容易引入的副作用）
- **CONN-D4b**·P1 详情页 + 真实连接 ⇒ 详情页订阅正常（守住既有行为）

### 11.3 修复达标标准

- **D1**：D1 PASS **且 K1/K3 仍 PASS**。仅"把 `started` 去掉"不算通过——必须让 `loadPairing()` 在写入不可见的窗口内**等待或重试**，而非一次性早退。
- **D2**：D2 PASS。可接受：① 去掉一次性 `started` 闸门改为按需重入；② 保留闸门但在配对可用时**主动触发重试**。**不可接受**：简单去掉闸门导致 K3 重复建连。
- **D3**：D3 PASS。可接受位置：`DshRemoteApp.onCreate`（读配对后 start）或 `MainActivity` 启动即检查并 start；**不接受**"必须重新走一次配对页"。
- **D4**：D4 PASS。可接受：把状态提升为全局可观察（服务单例/共享 ViewModel），列表页与详情页共同订阅；**D4b 必须仍 PASS**。
- **整体**：自动化用例全绿 **+** 模拟器复验（连接状态由"未连接"变"已连接"，贴截图或 `dumpsys` 证据）。

### 11.4 CONN-D6：扫码功能失效（真机专属缺陷，模拟器测不出）

**现象判据**：权限链路正常（无权限时点「打开扫码」会正确弹框），但**授权后没有真正启动相机**——`dumpsys media.camera` 的 Active Camera Clients 为 `[]`、logcat 无任何 CameraX/Camera2 日志。根因见 `android-app/.../core/CameraPermissionGate.kt` 文件头注释：旧实现 `Screen` 枚举无 SCANNER，按钮在任何情况下只调 `requestPermission`；权限已授予时系统不弹框也不回调 ⇒ 点击毫无反应。

**机器可判定判据**：

- **CONN-D6-a**·P0 `pm revoke` 后首次点「打开扫码」（`CAMERA` granted=false） ⇒ **弹出权限对话框**（人工确认一次即可）
- **CONN-D6-b**·P0 `pm grant` 后**第二次**点「打开扫码」 ⇒ **不崩溃、不 ANR**（crash buffer 无 `AndroidRuntime`/`ANR in com.deepseek.dshremote`）
- **CONN-D6-c**·**P0 ⭐** `dumpsys media.camera` → `Active Camera Clients` ⇒ **出现本 App 的 client**（不再为 `[]`）——**核心机器判据**
- **CONN-D6-d**·P1 logcat 过滤 `CameraX|Camera2|CameraDevice|CameraCaptureSession` ⇒ 出现相机绑定/会话创建日志（辅证）
- **CONN-D6-e**·P1 授权后直接点第二次 ⇒ UI dump 出现扫码页/相机预览（或等价"已进入扫码"标识）；若实现为"授权后自动进入"，第二次点击不得崩溃或重复跳转
- **CONN-D6-f**·P1 重复授权/取消授权循环 3 次 ⇒ 每次都能进入扫码页，无状态残留卡死
- **CONN-D6-g**·P1 进入扫码页后 `input keyevent 4`（返回）再进入 ⇒ **第二次仍能打开相机**（守卫：修复不得靠一次性标志）
- **CONN-D6-h**·P1 权限被撤销后（`pm revoke`）再点 ⇒ 重新弹出权限请求，不崩溃

**修复达标标准**：D6-c PASS（硬指标）+ D6-d PASS（辅证）+ D6-b/e/f/g/h 全部 PASS；语义明确为「首次点击 → 请求权限；授权后再次点击（或自动）→ 进入扫码页」，**不得出现"授权成功但仍停留原页且无任何反馈"**。

> ⚠ **易漏点**：验证时**必须点两次**。只点一次就判"扫码坏了"→ 假阴性；只看到权限弹窗就判"好了"→ 假阳性。
